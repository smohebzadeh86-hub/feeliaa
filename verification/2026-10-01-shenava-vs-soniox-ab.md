# 2026-10-01 — A/B: Shenava-Koochik (آفلاین) در برابرِ Soniox async (مسیرِ فعلیِ فیلیا)

> Evidence (مشاهده در یک زمان). فقط دادهٔ عمومی/ساختگی؛ هیچ دادهٔ مراجع. اسکریپت‌ها در scratchpadِ نشست (خارج از repo).

## سؤال
مالک: آیا Shenava (مدلِ آفلاینِ فارسی، Apache-2.0) رونویسیِ فیلیا را بهتر می‌کند؟

## روش
- **Shenava:** `PersianML/Shenava-Koochik-v1.0-sherpa-onnx` (۴۶۰MB، CTC آفلاین، بدونِ punctuation/diarization، اعداد حرفی ⇒ `persian_itn.py`)، sherpa-onnx روی CPU (i5-13420H، ۴ thread).
- **Soniox:** دقیقاً `transcribeFileAsync` خودِ فیلیا (`stt-async-v5`، diarization + contextِ جلسه) — فایل پس از هر اجرا از Soniox پاک شد.
- **داده‌ها:**
  1. FLEURS-fa dev، ۶۰ جمله‌ی واقعیِ انسانی (۹۲۴ث، گفتارِ خوانده‌شده) — «تمیز» و «نویزی»: پینک‌نویز + opus 24kbps (تقلیدِ ضبطِ durable؛ نویزِ **ساختگیِ من**، نه ضبطِ واقعی).
  2. سه گفت‌وگوی ساختگیِ TTS (۲–۳ دقیقه) با متنِ مرجع: `conv2w`، `convind` (مکث/تکرار/عدد)، `conv3`.
- نرمال‌سازیِ یکسان برایِ هر دو سو (حذفِ punctuation/برچسبِ گوینده، نیم‌فاصله→فاصله، ی/ک عربی، اعداد→رقم). متریک: WER/CER با `jiwer`.

## نتایج
| مجموعه | Shenava | Soniox async |
|---|---|---|
| FLEURS تمیز — WER / CER | 9.11% / 3.16% | **7.22% / 2.28%** |
| FLEURS تمیز — میانه‌ی WER هر جمله | 7.6% | **4.4%** |
| FLEURS نویزی+opus24k — WER | 27.5% | **23.8%** |
| conv2w (TTS) | 3.4% | **3.0%** |
| convind (TTS، مکث/عدد) | 9.1% | **1.1%** |
| conv3 (TTS) | 6.4% | **3.8%** |
| سرعت (RTF، CPU) | ~0.05–0.17 (۶–۲۰ برابر سریع‌تر از زمانِ واقعی) | سرویسِ ابری |

- بردِ جمله‌به‌جمله روی FLEURS تمیز: Shenava ۶ برد / ۲۷ مساوی / ۲۷ باخت.
- عددِ مدل‌کارت (FLEURS کامل: 10.64%) با عددِ ما (9.11% روی نمونه‌ی ۶۰تایی) هم‌خوان است ⇒ اجرای ما معتبر است.
- خطاهایِ نمونه‌ی Shenava: «کمکم»→«کم کم»، «که»→«چه»؛ حذفِ «اِ…» و تکرار؛ بدونِ punctuation.
- **سوگیریِ احتمالی به سودِ Shenava:** FLEURS/دادهٔ عمومی ممکن است در آموزشش بوده باشد؛ باز هم Soniox بهتر شد.

## آزمایشِ ایده: Shenava به‌عنوانِ «نظرِ دوم» (نه جایگزین)
اختلافِ کلمه‌ایِ Soniox↔Shenava به‌عنوانِ پرچمِ «احتمالاً غلط» (روی خروجیِ Soniox):

| شرایط | نرخِ غلطِ Soniox | recall (غلط‌هایی که پرچم خورد) | precision (پرچم‌هایی که واقعاً غلط بود) |
|---|---|---|---|
| تمیز | 6.5% | 40% | 45% |
| نویزی | 12.8% | 79% | 64% |

یعنی پرچم‌ها ۷× (تمیز) تا ۵× (نویزی) غلیظ‌تر از نرخِ پایه‌اند. این مکمل `markUncertainTokens` (که فقط از confidenceِ خودِ Soniox می‌آید) است؛ اندازه‌گیریِ همپوشانی با confidence انجام نشد (توکن‌های confidence ذخیره نشده بود).

## محدودیت‌ها (صادقانه)
- هیچ ضبطِ مکالمه‌ی واقعیِ درمانی (هم‌پوشانی، محاوره‌ی طبیعی، میکروفونِ اتاق) نبود؛ TTS و گفتارِ خوانده‌شده نماینده‌ی ضعیفی‌اند. نویزِ «واقعی» سنجیده نشد.
- فقط مسیرِ **آفلاین/batch** سنجیده شد؛ نسخه‌ی streaming (Rizeh) و latencyِ زنده سنجیده نشد.
- diarization: Shenava ندارد ⇒ مقایسه فقط متنی است.

## پیگیری: پیاده‌سازیِ «نظرِ دوم» و سنجشِ انتها‌به‌انتها

### کالیبراسیونِ قاعده (توکن‌هایِ واقعیِ Soniox با confidence، ۶۰ جمله، سطحِ واژه)
| قاعده | تمیز: flagged / recall / precision | نویزی: flagged / recall / precision |
|---|---|---|
| A) confidence<0.5 (رفتارِ فعلیِ `markUncertainTokens`) | 1.6٪ / 9٪ / 38٪ | 7.8٪ / 47٪ / 75٪ |
| B) فقط اختلاف با Shenava | 5.8٪ / 40٪ / 45٪ | 15.5٪ / 79٪ / 63٪ |
| D) اختلاف ∧ conf<0.9 | 2.5٪ / 22٪ / 58٪ | 10.1٪ / 64٪ / 79٪ |
| **E) اختلاف ∧ conf<0.97 (انتخاب‌شده)** | 3.2٪ / 29٪ / 61٪ | 11.2٪ / 69٪ / 77٪ |
نتیجه: confidenceِ فعلی روی صدای تمیز فقط ۹٪ غلط‌ها را می‌گیرد؛ E آن را ≈۳× می‌کند بی‌آنکه واژه‌هایِ زیادی علامت بخورد.

### کد (پشتِ `STT_SECOND_OPINION=1`، پیش‌فرض **خاموش**، fail-open)
`server/src/features/transcription/secondOpinion/{align,shenava,index}.ts` + وصل در `audio-upload/worker.ts#getText(id, audioPath)` (پورتِ `getText` یک پارامترِ اختیاری گرفت).
فقط confidenceِ توکن‌هایِ مشکوک صفر می‌شود؛ متنِ خام، `lowConfRatio` و هشدارِ کیفیت بدونِ تغییر. `sherpa-onnx-node` به‌صورتِ `optionalDependencies`.

### تستِ انتها‌به‌انتها (کدِ واقعیِ TS: ffmpeg ← sherpa-onnx-node/Shenava ← `markedTextFromTokens`؛ ۶۰ جمله)
| | قبل (فقط Soniox) | بعد (+نظرِ دوم، 0.97) | بعد (0.90) |
|---|---|---|---|
| تمیز: flagged / recall / precision | 1.0٪ / 5٪ / 33٪ | 4.3٪ / **24٪** / 37٪ | 3.4٪ / 20٪ / 38٪ |
| نویزی: flagged / recall / precision | 7.3٪ / 43٪ / 74٪ | 12.7٪ / **65٪** / 64٪ | 11.3٪ / 62٪ / 69٪ |
- زمان: میانه‌ی ۰٫۴ث برایِ هر جملهٔ ≈۱۵ثانیه‌ای (۴ thread). `decodeAsync` ⇒ event loop بلاک نمی‌شود.
- اعدادِ انتها‌به‌انتها کمی پایین‌تر از کالیبراسیونِ پایتونی‌اند (LCS به‌جایِ difflib؛ علامتِ سطحِ واژه‌ی خام؛ union با قاعده‌ی A) — صادقانه گزارش می‌شود: **۵× recall روی تمیز، ۱٫۵× روی نویزی، با کاهشِ precision روی نویزی (۷۴→۶۴٪)**.
- هنوز سنجیده نشد: ضبطِ واقعیِ ساعت‌ها (تکه‌بندی و زمان روی ۶۰ دقیقه)، بارِ CPUِ سرورِ production، اثرِ ⟦…؟⟧ِ بیشتر روی نگهبانِ `uncertain`ِ polish («متنِ نهایی») — پیش از روشن‌کردن در production باید با یک ضبطِ واقعیِ اجازه‌دار سنجیده شود.

## تستِ ضبطِ واقعی (تصمیمِ مالک: «فقط اگر واقعاً ارزشمند است»)
- **ضبط:** ۷ تکه‌ی ۱۵ثانیه‌ایِ جلسه‌ی تستِ خودِ مالک در dev (`ec144271`، ۲ گوینده، گفتگوی محاوره‌ایِ واقعی با نویز و هم‌پوشانی، ≈۹۰ث، ۲۴۰ واژه). مسیرِ واقعیِ فیلیا (Soniox async، contextِ جلسه) + `withSecondOpinion`. فایل از Soniox پاک شد؛ صدا/متن در repo نیست و scratchpad پاک شد.
- **نتیجه:** علامت‌گذاریِ فعلی (conf<0.5) **۲۶ واژه (۱۱٪)** را علامت می‌زد؛ با نظرِ دوم **۹۰ واژه (۳۷٫۵٪)** — ۲٫۵ برابر؛ ۶۴ واژه‌ی اضافه که Soniox دربارشان confidence بالای ۰٫۵ داشت.
- **علت (از مقایسه‌ی دو متنِ کامل):** Shenava روی گفتارِ محاوره‌ایِ واقعی بسیار ضعیف‌تر است (جمله‌هایِ بی‌معنا/بریده، مثلاً «دخترخت نبود دمون بسته بود»، «بیست بیست و دو خب چرا ما مثلا که چرا پنج»)، درحالی‌که متنِ Soniox روان و منسجم است. پس اغلبِ «اختلاف‌ها» غلطِ **Shenava** است نه Soniox ⇒ precisionِ واقعی روی این نوع صدا پایین است.
- **نتیجه‌گیری:** نتیجه‌ی FLEURS/TTS (گفتارِ خوانده‌شده/تمیز) روی صدایِ واقعیِ جلسه تعمیم نمی‌یابد. علامت‌گذاری رویِ ۳۷٪ متن برایِ polish و تراپیست بی‌فایده/مضر است. **ارزشمند نیست ⇒ روشن نمی‌شود.** (قضاوتِ واژه‌به‌واژه با گوشِ انسانی انجام نشد؛ این نتیجه بر اساسِ نرخِ علامت و کیفیتِ مشهودِ متنِ Shenava است.)
